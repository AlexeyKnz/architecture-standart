### Название задачи: Концептуальная архитектура MVP открытия депозитов
### Автор: Архитектор
### Дата: 2024.03.20

### Функциональные требования

| № | Действующие лица или системы | Use Case | Описание |
|:-:|:-----------------------------|:---------|:---------|
| 1 | Клиент, Сайт | Подача заявки на депозит через сайт | Клиент оставляет ФИО и номер телефона для обратного звонка |
| 2 | Клиент, Интернет-банк | Подача заявки на депозит через интернет-банк | Авторизованный клиент выбирает счет, сумму и подтверждает операцию SMS |
| 3 | Менеджер кол-центра | Обработка заявки с сайта | Менеджер видит заявку в CRM и связывается с клиентом |
| 4 | Менеджер бэк-офиса | Обработка заявки на депозит | Ручное подтверждение условий депозита в АБС |
| 5 | АБС | Расчет персонализированных ставок | Автоматический расчет ставок на основе данных клиента |
| 6 | SMS-шлюз | Отправка уведомлений клиенту | Отправка SMS на ключевых этапах процесса |

### Нефункциональные требования

| № | Требование |
|:-:|:----------|
| 1 | Доступность 24/7 с uptime 99.9% |
| 2 | Время отклика операций < 100 мс |
| 3 | Шифрование передаваемых данных |
| 4 | Горизонтальное масштабирование интернет-банка |
| 5 | Совместимость с существующими СУБД (MS SQL, Oracle) |
| 6 | Избежание прямой интеграции с АБС |
| 7 | Использование технологий с имеющейся экспертизой |

**Логика принятия решений:**

1. **Разделение ответственности:** Создан отдельный Сервис ставок для изоляции сложной логики расчета от АБС
2. **Асинхронная коммуникация:** Использование Message Broker для избежания прямой интеграции с АБС
3. **Кэширование:** Введен Кэш ставок для обеспечения производительности < 100 мс
4. **Безопасность:** Единый API Gateway обеспечивает шифрование и аутентификацию
5. **Технологический стек:** Выбор основан на существующей экспертизе банка (Java Spring Boot, React.js, Oracle)

### Альтернативы

**Альтернатива 1:** Прямая интеграция с АБС
- *Недостатки:* Риск перегрузки АБС, нарушение требования R+2
- *Ограничения:* Невозможность обеспечить требуемую производительность

**Альтернатива 2:** Полная микросервисная архитектура
- *Недостатки:* Высокая сложность реализации для MVP
- *Риски:* Нехватка экспертизы у команды

**Недостатки, ограничения, риски**

1. **Сложность интеграции:** Необходимость синхронизации данных между разными СУБД
2. **Производительность Message Broker:** Риск стать узким местом при высокой нагрузке
3. **Обучение команды:** Необходимость обучения работе с новыми компонентами (Kafka, Redis)
4. **Мониторинг:** Усложнение системы мониторинга из-за распределенной архитектуры
5. **Отказоустойчивость:** Зависимость от множества компонентов увеличивает риски сбоев
